# 性能与并发优化执行方案（效果优先版）

## 1. 背景与目标

当前 `33` 条 `smoke` 跑批在实际执行中耗时过长。已完成的 `31` 条统计表现为：

- 平均耗时约 `316.95s`
- 中位耗时约 `242.48s`
- 最长耗时约 `1451.55s`

现阶段问题不是单点 bug，而是以下几类因素叠加：

1. `benchmark` 按样本串行执行，总耗时为单样本耗时累加
2. `Stage 2` 为 `(chunk, rule)` 粒度深判，单样本可能触发多次 LLM 调用
3. `Filter` 失败后会直接放行 `Top-20` 候选，导致后续精判数量膨胀
4. 全文审核 `Stage 2.6` 目前串行挂在主流程后半段，不能与主流程重叠
5. `think + 10000 tokens + 240s timeout + retries` 使长样本尾部延迟极大

本方案目标不是“只追求更快”，而是：

- **优先不降低审核效果**
- **削减无效等待和无效候选**
- **把可并行的流程并行起来**
- **保留高风险场景的审慎判定**

---

## 2. 当前瓶颈拆解

### 2.1 Filter 失败后的候选爆炸

当前逻辑：

- 正常情况：`Top-20 -> Filter -> Top-3`
- 异常情况：`Top-20 -> Filter 失败 -> 全量 Top-20 下放`

这会让单样本的 `Stage 2` 深判数量从 `3~6` 直接抬到 `15~20+`，是当前长尾耗时的重要来源。

### 2.2 全文审核未与主流程重叠

当前 `Stage 2.6` 在 `Stage 2.5` 之后执行。  
但它实际上只依赖：

- `document`
- 全文信号提取结果

并不依赖 `Stage 2` 主判定结果。因此这部分等待是可以重叠的。

### 2.3 并发使用在局部，但没有形成全局调度

当前已有并发：

- `Stage 1`：按 chunk 并发 filter
- `Stage 2`：按 skill pair 并发深判

但缺少两层关键调度：

1. 主流程与全文审核之间的并行调度
2. benchmark 样本之间的有限并行调度

### 2.4 不是“没有协程”，而是“没有在最值钱的地方削峰”

当前慢的本质不是协程缺失，而是：

- 候选数量先膨胀
- 再让并发去消费膨胀后的任务
- 结果并发没有减小总工作量，只是把部分等待并行化

---

## 3. 核心优化方向

## 3.1 P0：Filter 失败后的候选压缩机制

### 目标

避免 `Filter` 失败时直接把 `Top-20` 原样放入 `Stage 2`。

### 原则

- 不做“激进裁剪”
- 不直接砍掉高风险类别
- 优先做“结构性去重”和“规则族压缩”

### 建议策略

当 `Filter` 调用失败时，走 `fallback_compress()`：

1. 保留所有高优先级、高风险候选
2. 按 `audit_point_id` 去重
3. 按 `(primary_category, secondary_category)` 去重
4. 同规则族仅保留最相关的前 `1~2` 条
5. 对最终下放数设置上限，例如 `6~8`

### 推荐的压缩优先级

1. 明确命中 `condition_terms` 的规则
2. 命中词数量更多的规则
3. 命中跨度更集中、证据更短的规则
4. 有明确 `audit_point_id` 的规则

### 为什么这项风险低

- 不是减少召回入口，而是减少“同质候选重复打 LLM”
- 保留高风险规则与多证据规则
- 比直接放行 `Top-20` 更合理

### 验收标准

- `Filter` 失败样本中，`Stage 2` pair 数量明显下降
- 误报/漏报不出现系统性恶化
- 慢样本耗时出现显著下降

---

## 3.2 P0：全文审核 Stage 2.6 并行启动

### 目标

让 `Stage 2.6 full_document_audit` 与主流程重叠执行，而不是串行等待。

### 推荐时机

在 `Stage 0` 完成后即可启动异步任务。

原因：

- `Stage 2.6` 只依赖 `document`
- 不依赖 Stage 1/1.5/1.8/1.9/2 的结果

### 推荐实现

在 workflow 中增加并行 future：

1. `Stage 0` 完成后创建 `fulldoc_task`
2. 主流程继续执行 `Stage 1 -> Stage 2.5`
3. 在进入 `Stage 2.7` 前 `await fulldoc_task`
4. 合并 `state.stage26_full_document_judgments`

### 并发约束

必须与主流程共享统一预算，而不是额外无限放大：

- `FULLDOC` 与 `Stage 2 skill` 共用总 LLM 预算
- 推荐采用单独 semaphore 或全局调度器

### 风险控制

- 如果文档无数据引用或引用全部有来源，仍直接零成本跳过
- 不改变全文审核判定标准，只改变启动时机

### 为什么这项风险低

- 不改变全文审核判定逻辑
- 不减少信息输入
- 只是消除不必要的串行等待

---

## 3.3 P1：主流程全局并发调度

### 目标

把并发从“局部并发”升级成“全局受控并发”。

### 当前问题

当前各处并发虽然存在，但预算是分散理解的：

- `Stage 1` 的 filter 并发
- `Stage 2` 的 skill 并发
- `Stage 2.6` 的全文审核

缺少统一调度会导致：

- 某些阶段抢占全部调用预算
- 慢调用拖住后续步骤
- 长尾样本造成整体吞吐下降

### 推荐方案

引入统一的“运行时预算层”：

- `GLOBAL_LLM_SEMAPHORE`
- `FAST_LANE`：filter / semantic prescreen
- `HEAVY_LANE`：judge / base_verify / full_document_audit

### 推荐配比

- `filter` 占轻量通道，永远优先返回
- `judge/base_verify/full_document` 共用重量通道
- `full_document` 默认最多占 `1` 个重通道

### 效果

- 避免全文审核或少数超重 skill 抢满全部并发
- 减少长尾积压

### 风险

- 这一项涉及调度层改动，优先级低于前两项
- 需要额外回归验证，不建议第一步就大动

---

## 3.4 P1：benchmark 样本级有限并行

### 目标

减少跑批总耗时，而不改变单样本内流程逻辑。

### 当前问题

`benchmark.runners.run_sdk` 对数据集是串行执行：

- 一个样本跑完才开始下一个样本

### 推荐方式

样本级并行度控制在低水平，例如：

- `2`
- `3`

不要直接放大到 `8+`，否则会放大：

- TPM 限流
- 结构化输出失败
- JSON 救援重试

### 风险控制

- 样本间并行只作用于 benchmark，不改变线上单文档审核逻辑
- 需要单独配置，不默认复用线上参数

---

## 4. 不建议当前立刻做的事

以下方案虽然可能提速，但当前存在明显效果风险，建议暂缓：

### 4.1 直接缩小 `max_tokens`

当前很多复杂判定已经证明对输出预算敏感。  
贸然减小 `max_tokens` 容易带来：

- 结构化 JSON 不完整
- reasoning 被截断
- `unsure/compliant` 偏保守

### 4.2 直接关闭 `judge think`

当前项目中复杂技能（金融混淆、合同外利益、责任夸大）仍较依赖深层语义判断。  
直接关掉 `judge think` 风险较高。

### 4.3 直接把 Gate 改成大规模前置跳过

虽然会提速，但容易伤召回。  
当前更适合先优化“Filter 失败后的候选压缩”，再考虑更激进裁剪。

### 4.4 直接用小模型替换主 Judge

当前明确不采用。

---

## 5. 推荐实施顺序

## P0（先做）

1. `Filter fallback` 候选压缩
2. `Stage 2.6` 并行启动

这两项组合能带来最大收益，而且对审核效果风险较低。

## P1（第二批）

3. 全局并发预算层
4. benchmark 样本级有限并行

这两项更偏系统调度优化，收益稳定，但改动范围更大。

---

## 6. 验收指标

优化完成后建议至少比较以下指标：

### 效果指标

- Precision
- Recall
- F1 / F2
- 类别命中率
- 定位模糊命中率

### 性能指标

- 单样本平均耗时
- 单样本 P90 耗时
- 最长样本耗时
- 每样本平均 `Stage 2` pair 数
- Filter 失败样本的平均下放候选数

### 特别关注

- `financial_confusion`
- `gifts_or_extra_benefits`
- `responsibility_exaggeration`

这些类别在当前慢样本里贡献最大，也最容易被错误“提速”伤效果。

---

## 7. 最终判断

针对当前问题，最值得先做的不是简单“缩配置”，而是：

1. **减少无效候选进入 Stage 2**
2. **让全文审核与主流程重叠执行**
3. **把并发从局部优化成受控调度**

这样做的好处是：

- 提速来自“减少无效工作”和“消除串行等待”
- 不是来自“减少模型理解能力”
- 更符合当前项目“审核效果优先”的目标
